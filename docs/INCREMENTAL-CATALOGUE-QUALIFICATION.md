# Incremental catalogue qualification

Status: development implementation and qualification; production serving remains on the full builder.

The shadow processor captures coalesced observer/prefix dirty keys in the source transaction. An observer lock precedes queue locks, matching ingestion; a consumer advisory lock prevents concurrent reference-count writers. Work is bounded by observer and key count. Source observer resets and source truncation block publication until a controlled reseed. The current seed and installation entry points are restricted to the dedicated qualification database. Do not apply this prototype migration to production.

Only changed routes, memberships and counts are maintained. Reference counts preserve distinct prefix and observer totals across viewpoints. Ordered-path transit and raw AS_SET treatment follow the existing builder. Unchanged memberships avoid writes. Previous changed rows are versioned to retain stable pinned views; publication-token expiry and bounded history deletion are implemented separately. The raw diagnostic journal is neither reduced nor replaced.

Validation includes randomized announcements/withdrawals and origin/path changes, IPv6/four-byte ASNs/AS_SET, observer isolation, exact full-recomputation comparisons, consumer rollback/retry, source transaction rollback, observer epoch reset, source truncation, stable pinned route/count versions and two independent database connections exercising commit visibility and lock ordering. Test-only reseeding invalidates prior qualification snapshots; a nonblocking production bootstrap and reset recovery are still required.

A synthetic 40,001-route fixture with 400 changed keys compared a full rebuild of routes, equivalent route indexes, memberships and ASN aggregates against incremental maintenance. First measured indexed-reference run: full 33,415,872 WAL bytes / 4.369 seconds; incremental 946,760 bytes / 0.682 seconds. Final route state and retained history matched. These are development workload measurements, not production spindle IOPS savings. Queue-capture overhead, million-route scale, long-running history retention and serving query plans remain qualification requirements.

The independent current-route index replay used the existing captured input, consolidation and unchanged UPSERT ordering. Removing the two timestamp B-trees, adding timestamp BRIN and using fillfactor 80 produced 357–367 HOT updates versus zero for the original indexes. All 2,616 final routes and provenance matched. First pair statement WAL was 4,756,468 versus 3,557,120 bytes; repeated pair 4,547,759 versus 4,130,250. The repeated candidate was slower (3.757 versus 2.676 seconds) and dirtied more buffers (347 versus 247). This is not a passing production promotion result. Chronological route query costs must be qualified before changing those indexes.

Remaining release gates: production-safe bootstrap and reset catch-up; bounded storage and ingest lock budgets; complete serving adapter and explicit lag/expiry responses; complete-source-sized replay and read-path qualification; production shadow comparison; reversible promotion; retire routine rebuilds only after those pass. Keep current production collection, journal evidence, retained browsing generations and fallback intact. Unrelated diagnostic UI/API work is outside this change.

Final analyzed read-path check: original chronological lookup 0.201 ms / 8 shared hits; BRIN candidate 38.392 ms / 860 shared hits on 40,001 synthetic routes. The candidate fails this read gate and is rejected for production. Final scale rerun retained exact routes/history: full 33,370,072 WAL bytes / 4.258 seconds; incremental 909,736 bytes / 0.962 seconds. Existing 112 native regressions passed. Private full logs are retained outside the repository.
